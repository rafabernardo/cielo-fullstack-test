# Backend API

Base URL: `http://localhost:8080/api`. JSON only, `camelCase` fields. Identifiers generated by this service are UUIDs;
timestamps are ISO-8601 `Instant`s (UTC); dates are `yyyy-MM-dd`; money is a decimal number.

With the backend running, the generated OpenAPI spec is at `http://localhost:8080/v3/api-docs` and Swagger UI at
`http://localhost:8080/swagger-ui.html`. This document stays the reference for error codes and duplicate rules.

| Method | Path                                                       | Purpose                                    |
|--------|------------------------------------------------------------|--------------------------------------------|
| `POST` | `/api/authorizations`                                      | Register a beneficiary's authorization     |
| `GET`  | `/api/beneficiaries/{beneficiaryId}/authorization`         | Check whether a beneficiary is authorized  |
| `GET`  | `/api/beneficiaries/{beneficiaryId}/schedule`              | List the beneficiary's installments        |
| `GET`  | `/api/beneficiaries/{beneficiaryId}/portability-operations`| List the beneficiary's operations (paged)  |
| `POST` | `/api/portability-operations`                              | Request portability of installments        |
| `GET`  | `/api/portability-operations/{id}`                         | Read an operation's status                 |
| `GET`  | `/api/portability-operations/{id}/events`                  | Stream an operation's status changes (SSE) |

Typical flow: check the authorization (create it if missing) → read the schedule → create a portability operation with
the eligible installments → follow it via `GET /{id}` (honouring `Retry-After`) or `/{id}/events` until it leaves
`PENDING`. Past operations are listed per beneficiary.

---

## `POST /api/authorizations`

Registers the beneficiary's authorization with the Central de Convênios and stores it locally. Required before the
schedule can be read.

**Request**

```json
{ "beneficiaryId": "12345678900" }
```

| Field           | Type   | Rules     |
|-----------------|--------|-----------|
| `beneficiaryId` | string | not blank |

**Response `201 Created`**

```json
{
  "id": "6f1c0e3a-5b8e-4a5e-9a51-1f0b1f6f2d10",
  "beneficiaryId": "12345678900",
  "centralAuthorizationId": "AUT-0001",
  "createdAt": "2026-11-08T12:00:00Z"
}
```

**Errors:** `400 VALIDATION_ERROR`, `502 CENTRAL_CONVENIOS_BAD_RESPONSE`, `503 CENTRAL_CONVENIOS_UNAVAILABLE`.

---

## `GET /api/beneficiaries/{beneficiaryId}/authorization`

Tells whether the beneficiary has an authorization stored locally. The Central is not called, so this read never fails
because of it.

**Response `200 OK`**

```json
{ "beneficiaryId": "12345678900", "authorized": true }
```

An unknown beneficiary answers `"authorized": false`, not `404`.

---

## `GET /api/beneficiaries/{beneficiaryId}/schedule`

Reads the beneficiary's future payroll deductions from the Central and marks which ones can be selected.

**Response `200 OK`**

```json
{
  "beneficiaryId": "12345678900",
  "installments": [
    {
      "installmentId": "INS-1",
      "agreementId": "AGR-9",
      "amount": 350.00,
      "deductionDate": "2026-12-05",
      "status": "OPEN",
      "eligible": true,
      "heldBy": null
    },
    {
      "installmentId": "INS-2",
      "agreementId": "AGR-9",
      "amount": 350.00,
      "deductionDate": "2027-01-05",
      "status": "OPEN",
      "eligible": false,
      "heldBy": { "operationId": "0b8e7a52-2a1c-4c39-8f7e-3f2a9a1d4e11", "status": "PENDING" }
    }
  ]
}
```

| Field      | Meaning                                                                                   |
|------------|-------------------------------------------------------------------------------------------|
| `status`   | `OPEN`                                                                                     |
| `eligible` | `true` when `OPEN` and `heldBy` is `null`                                                  |
| `heldBy`   | The `PENDING` or `CONFIRMED` operation holding the installment (`operationId`, `status`), or `null` |

**Errors:** `422 AUTHORIZATION_REQUIRED` (no authorization registered for the beneficiary),
`502 CENTRAL_CONVENIOS_BAD_RESPONSE`, `503 CENTRAL_CONVENIOS_UNAVAILABLE`.

## `POST /api/portability-operations`

Creates a portability operation and submits it to the Central. The outcome is asynchronous: the operation starts
`PENDING` and is followed in the background until the Central confirms or rejects it.

**Request**

```json
{
  "beneficiaryId": "12345678900",
  "installmentIds": ["INS-1", "INS-2"],
  "destinationAccount": { "bankCode": "341", "branch": "0001", "accountNumber": "123456-7" }
}
```

| Field                              | Type     | Rules                                                     |
|------------------------------------|----------|-----------------------------------------------------------|
| `beneficiaryId`                    | string   | not blank                                                 |
| `installmentIds`                   | string[] | required, no blank items, no duplicates; empty only when the schedule is empty |
| `destinationAccount.bankCode`      | string   | exactly 3 digits                                          |
| `destinationAccount.branch`        | string   | exactly 4 digits                                          |
| `destinationAccount.accountNumber` | string   | 1–12 digits, optional `-` check digit (`0-9`, `X`, `x`)   |

**Responses**

| Status         | When                                                                                                    |
|----------------|---------------------------------------------------------------------------------------------------------|
| `202 Accepted` | Operation submitted to the Central. `Location: /api/portability-operations/{id}`                        |

Body: a [portability operation](#portability-operation).

**Duplicates**

An installment belongs to at most one `PENDING` or `CONFIRMED` operation, enforced by a unique constraint. Any request
with an installment already held is refused with `409 INSTALLMENT_IN_PENDING_OPERATION` or
`409 INSTALLMENT_IN_CONFIRMED_OPERATION`, after the holder's status: a repeated request (double click, retry
after a lost response), the same installments with another account, or a partial overlap. `operationIds` names the
operations holding them, so the client can follow the existing operation. No `Idempotency-Key` is needed; one sent by an
older client is ignored. Once an operation ends `REJECTED` or `FAILED`, its installments are free and a new request
creates a new operation.

**Errors**

| Status | `code`                           | When                                                                                     |
|--------|----------------------------------|------------------------------------------------------------------------------------------|
| `400`  | `VALIDATION_ERROR`               | Body invalid or malformed                                                                |
| `409`  | `INSTALLMENT_IN_PENDING_OPERATION`   | Installments held by a `PENDING` operation; `installmentIds` lists them, `operationIds` the holders |
| `409`  | `INSTALLMENT_IN_CONFIRMED_OPERATION` | Installments held by a `CONFIRMED` operation; wins over pending, listing only the confirmed ones   |
| `422`  | `AUTHORIZATION_REQUIRED`         | No authorization registered for the beneficiary                                          |
| `422`  | `INSTALLMENT_NOT_ELIGIBLE`       | Installments missing from the schedule or not `OPEN`; `installmentIds` lists them. Also an empty `installmentIds` while the schedule has installments |
| `502`  | `CENTRAL_CONVENIOS_BAD_RESPONSE` | Central answered unexpectedly                                                            |
| `503`  | `CENTRAL_CONVENIOS_UNAVAILABLE`  | Central unreachable or timed out                                                         |

A `502`/`503` during the schedule check creates nothing. During submission it leaves the operation `FAILED` and frees
its installments. Either way, sending the request again is safe.

## `GET /api/portability-operations/{id}`

Returns the operation's current state. Status changes come from the background follow-up, not from this read.

**Response `200 OK`** — a [portability operation](#portability-operation). While `PENDING`, the response carries
`Retry-After: <seconds>` (≥ 1), when the next check against the Central is due; poll again after it.

**Errors:** `400` (`id` not a UUID), `404 PORTABILITY_OPERATION_NOT_FOUND`.

---

## `GET /api/beneficiaries/{beneficiaryId}/portability-operations`

Lists the beneficiary's operations, newest first (`createdAt`, then `id`, descending). Reads local data only.

| Query  | Default | Rules                                  |
|--------|---------|----------------------------------------|
| `page` | `0`     | zero-based                             |
| `size` | `5`     | capped at `20`                         |
| `sort` |         | ignored; the order is always newest first |

**Response `200 OK`**

```json
{
  "content": [ { "id": "0b8e7a52-…", "status": "PENDING", "…": "…" } ],
  "page": { "size": 5, "number": 0, "totalElements": 1, "totalPages": 1 }
}
```

Each `content` item is a [portability operation](#portability-operation). An unknown beneficiary answers an empty page,
not `404`.

---

## `GET /api/portability-operations/{id}/events`

Server-Sent Events stream (`text/event-stream`) of the operation's status.

- Sends one `status` event with the current state right after subscribing, then one after every committed change.
- Each event's `data` is a [portability operation](#portability-operation) as JSON.
- The server closes the stream once the operation leaves `PENDING`.
- Streams time out after `spring.mvc.async.request-timeout` (60s); `EventSource` reconnects and receives the current
  status again.

```
event:status
data:{"id":"…","status":"PENDING",…}

event:status
data:{"id":"…","status":"CONFIRMED",…}
```

```js
const source = new EventSource(`/api/portability-operations/${id}/events`);
source.addEventListener('status', (e) => {
  const operation = JSON.parse(e.data);
  if (operation.status !== 'PENDING') source.close();
});
```

**Errors:** `404 PORTABILITY_OPERATION_NOT_FOUND`, returned before any stream is opened.

## Portability operation

```json
{
  "id": "0b8e7a52-2a1c-4c39-8f7e-3f2a9a1d4e11",
  "beneficiaryId": "12345678900",
  "installmentIds": ["INS-1", "INS-2"],
  "destinationAccount": { "bankCode": "341", "branch": "0001", "accountNumber": "123456-7" },
  "status": "PENDING",
  "rejectionReason": null,
  "createdAt": "2026-11-08T12:00:00Z",
  "updatedAt": "2026-11-08T12:00:00Z"
}
```

| `status`    | Meaning                                                                    | Installments held |
|-------------|----------------------------------------------------------------------------|-------------------|
| `PENDING`   | Submitted, waiting for the Central's outcome                               | yes               |
| `CONFIRMED` | Central confirmed the portability                                          | yes, for good     |
| `REJECTED`  | Central rejected it; `rejectionReason` says why                            | no                |
| `FAILED`    | Submission failed, or the Central no longer knows the operation; a new `POST` creates a new operation | no |

```
PENDING ──▶ CONFIRMED
   │  └───▶ REJECTED
   └──────▶ FAILED
```

## Errors

Every error is an RFC 9457 problem (`application/problem+json`) with a machine-readable `code`:

```json
{
  "type": "about:blank",
  "title": "Unprocessable Content",
  "status": 422,
  "detail": "Installments are not in the beneficiary's schedule or are not eligible for portability.",
  "instance": "/api/portability-operations",
  "code": "INSTALLMENT_NOT_ELIGIBLE",
  "installmentIds": ["INS-3"]
}
```

| Status | `code`                            | Extra properties                     |
|--------|-----------------------------------|--------------------------------------|
| `400`  | `VALIDATION_ERROR`                | `errors`: `{ field: message }` (only for invalid fields, not for malformed bodies) |
| `404`  | `PORTABILITY_OPERATION_NOT_FOUND` |                                      |
| `409`  | `INSTALLMENT_IN_PENDING_OPERATION`   | `installmentIds`, `operationIds`  |
| `409`  | `INSTALLMENT_IN_CONFIRMED_OPERATION` | `installmentIds`, `operationIds`  |
| `422`  | `AUTHORIZATION_REQUIRED`          |                                      |
| `422`  | `INSTALLMENT_NOT_ELIGIBLE`        | `installmentIds`                     |
| `502`  | `CENTRAL_CONVENIOS_BAD_RESPONSE`  |                                      |
| `503`  | `CENTRAL_CONVENIOS_UNAVAILABLE`   |                                      |
| `500`  | `INTERNAL_ERROR`                  | generic message, no internals        |

Other Spring MVC errors (unknown route, wrong method, unsupported media type, bad path variable) use the HTTP status
name as `code`, e.g. `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `UNSUPPORTED_MEDIA_TYPE`, `BAD_REQUEST`.
